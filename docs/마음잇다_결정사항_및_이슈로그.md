## 2. 아직 안 끝난 것 - 다음 논의에서 이어가야 할 이슈

1. **일간 vs 주간 알림 트리거 통합 여부** — **해결됨.** 요구사항정의서 재수정판 UC-10 선행조건에 "본 알림은 일간 정서지수 산출 시점에만 트리거되며, 주간 리포트(UC-08)는 별도 알림 없이 조회 전용으로 제공된다"로 명시됨. 즉 "일간/주간 두 알림 타입으로 분리"가 아니라 **알림 자체가 일간 트리거 하나뿐이고 주간은 알림 없이 조회만 제공**하는 것으로 정리됨.

2. **알림 `target` 스키마 확장**
   **부분 해결.** 최종 요구사항정의서 UC-11 기본흐름③에 알림 목록 반환 필드가 "유형, 제목, 내용, 대상(리포트 등)" 4-튜플로 구체화되었고, FR-03-04에 알림 유형 3종(연결 요청 / 정서지수 하락 / 리포트 도착)이 명시됨. 다만 유형별 `target` 필드의 실제 타입 정의(예: `{type:'dailyReport', reportId}` 같은 스키마)는 여전히 없음 — `packages/shared-types` 설계 시 확정 필요.

3. **근거 문장(evidenceSentences) 소스 범위** — **해결됨.** 요구사항정의서 재수정판에서 UC-09/FR-03-02가 범위를 명시적으로 넓힘: "척도(SGDS-K/GAD-7/LSNS-6) 태그가 부여된 발화는 반드시 포함하며, 척도 태그가 없더라도 실시간 감성분석 결과(`sentiment_label`)가 있는 발화는 해당 라벨과 함께 ... 노출해야 한다"(FR-03-02). 이제 화면 목업(전체 대화 노출)과 문서 스펙이 일치함. 단 여기 쓰이는 건 `sentiment_label`뿐이고 `sentiment_note`는 근거문장 노출과 무관(UC-06-4 일간 요약 생성에만 쓰임) — 혼동하지 말 것.

4. **문서 내 오탈자** — **해결됨.** DB는 MySQL로 통일(위 표 참고). 3개 원본 문서 표지 날짜도 모두 2026.08.28로 통일되어 역전 문제 해소. (참고: 화면설계서 내부 변경이력 표의 최신 리비전(v0.3)이 2026.08.03으로 표지 날짜보다 앞서 있는 사소한 불일치가 남아있으나, 별도 조치 불필요한 수준)

5. **`voice_score` 이름 충돌** — **해결됨.** 팀 결정: turn 단위 `voice_score`/일간 집계 `VoiceScore` 개념 자체를 없앤다. 음성 acoustic feature(톤·피치)는 별도로 수치화하지 않고, UC-04의 실시간 감성분석(`sentiment_label`/`sentiment_note` 생성) 입력 재료로만 사용한다. 정서지수(UC-06-2)는 **TextScore 단일값**으로 산출한다. 요구사항정의서의 "정서지수 = TextScore × 0.7 + VoiceScore × 0.3" 공식과 UC-06-3(음성 톤·피치 비언어적 지표, 0~100 acoustic score) 자체는 문서 원문에 그대로 남아있지만, 실제 구현은 이 결정을 따른다 — 이 부분은 문서를 따르지 말 것.

## 3. 참고 사항 (별도 조치 불필요)

- 시스템 아키텍처 다이어그램(클라이언트 - 백엔드 API 서버 - AI 서버 - MySQL DB - 알림 서버 4계층 구조)은 위 3개 문서 내용만을 시각화한 것으로, 로드밸런서·캐시·CDN 등 인프라 요소는 문서에 명시되지 않아 제외됨. 실제 배포 인프라가 정해지면 별도로 그릴 것.
- 요구사항정의서의 `UC-06-04`는 자체 스펙 헤딩에만 등장하는 오기 표기이고, 문서 내 다른 모든 교차 참조(예: UC-04 step 6)는 `UC-06-4`(한 자리)로 쓴다. 코드/타입/커밋 메시지에서는 `UC-06-4`로 통일할 것.
- UC-06-1/UC-07 본문에 남아있는 "세션" 표현은 이전 버전의 잔존 오기다. **"conversation 단위로 이해할 것"도 더 이상 맞지 않는다 — §5(2026-08-05)에서 "대화(conversation)" 컨테이너 개념 자체가 삭제되고 turn이 독립적인 이력 단위가 됐으므로, "세션"이든 "conversation"이든 이 단어가 나오면 무시하고 turn 단위로 이해할 것.** `Conversation`, `conversationId`, `startedAt`, `endedAt`은 신규 코드에 쓰지 않는다.
- NFR-RE-001(실시간 연결 끊김 예외 처리) 문구의 "대화 종료 시 정서지수 재계산 트리거"는 conversation 개념 삭제로 더 이상 성립하지 않는 표현이다 — **"대화 종료"라는 이벤트에 재계산을 의존하지 않는다.** 실제로는 turn이 저장될 때마다 해당 turn의 귀속 날짜(§5의 answeredAt 기준) 리포트를 "갱신 대상"으로 표시해두고, 일간 리포트 생성 작업이 그 날짜에 귀속된 모든 유효 turn을 다시 조회해 재집계하는 방식으로 처리한다. WebSocket 연결이 끊기는 것(재연결 처리, NFR-RE-001 원래 취지)과 "대화가 끝났다"는 개념은 서로 무관하다 — 연결이 끊겨도 이미 저장된 turn들은 각자의 귀속 날짜 리포트에 정상적으로 집계된다.

## 4. 향후 확장 대비 아키텍처 원칙

> 팀 전체가 공식적으로 확정한 요구사항은 아니고, 외부 조언을 받아 개발 방향에 반영하기로 한 엔지니어링 원칙. MVP는 웹으로만 구현하되, 나중에 Flutter 앱을 추가할 때 백엔드/AI서버를 다시 짜지 않아도 되도록 아래를 지킨다.

- 백엔드(NestJS) REST API는 OpenAPI(Swagger) 스펙으로 관리 — 추후 Flutter(Dart)용 클라이언트를 스펙 기반으로 생성 가능하게 함
- 실시간 안부 대화 WebSocket 이벤트명·payload 구조는 `packages/shared-types`에 타입으로 고정 — 프론트엔드 코드 안에만 암묵적으로 존재하지 않도록 함
- 인증은 브라우저 쿠키/세션이 아닌 JWT 등 토큰 기반으로 구현 — 모바일 클라이언트도 동일한 인증 흐름 재사용 가능하게 함
- 정서지수 계산, 임계치 판단, 권한 체크 등 비즈니스 로직은 프론트엔드(React)가 아닌 백엔드/AI서버에 위치 — 새 클라이언트가 로직을 재구현할 필요 없게 함

## 5. 2026-08-05 추가 결정사항

- **일간 리포트 집계 단위: turn 단위로 변경(§3의 conversation_id 통합 귀속 규칙 폐기).** 하루의 경계는 서비스 기준 시간대(Asia/Seoul)의 `[당일 00:00, 익일 00:00)` 반개구간이며, DB 저장은 UTC ISO 8601, 일간 조회 요청은 `YYYY-MM-DD`(서비스 기준 시간대)로 받아 백엔드가 UTC 범위로 변환한다. 자정을 넘겨 진행된 통화는 더 이상 시작 시각 기준으로 전체가 한쪽 날짜에 묶이지 않고, turn별로 각자의 귀속 시각이 속한 날짜에 개별 귀속된다 — 하나의 통화가 두 날짜의 리포트에 걸쳐 분리 집계될 수 있다. **귀속 기준 시각은 `createdAt`(질문 생성 시각)이 아니라 `answeredAt`(시니어가 실제 답변한 시각)이다** — `createdAt`은 무한 스크롤 정렬/페이지네이션에만 쓴다. 답변 없이 끝난 turn만 `createdAt`으로 대체 귀속한다(예: 23:59에 질문이 생성됐고 00:01에 답했다면, `answeredAt` 기준으로 "다음날" 리포트에 잡혀야 한다 — 실제 감정 신호가 발생한 시점이 그때이기 때문). 리포트 재생성 시 해당 날짜에 귀속된 모든 유효 turn을 다시 모아 재집계한다.
- **"대화 세션" 컨테이너 개념 삭제.** 여러 turn을 하나의 통화 단위(`Conversation`: `startedAt`/`endedAt`)로 묶는 개념 자체를 없앤다. turn이 독립적인 이력 레코드가 되며, 이 결정에 따라 `packages/shared-types`에 `ConversationTurn` 타입(자체 `createdAt` 포함)을 최초로 고정했고 `apps/frontend`의 `entities/conversation`도 이를 재노출하도록 맞췄다. 단 `entities/user`의 `SessionProvider`/`useSession`은 로그인 인증 세션이라 이번 삭제와 무관 — 계속 유지한다.
- **이전 대화 이력 무한 스크롤.** 시니어 안부 대화 화면(`SENIOR_CONVERSATION_01`)에서 과거 turn 이력을 무한 스크롤로 조회 가능해야 한다. cursor pagination 계약(`createdAt`+`id` 기반), 실시간 WebSocket으로 들어오는 turn과 REST로 가져온 과거 이력의 병합·중복 제거 규칙은 별도 feature 브랜치에서 `packages/shared-types`에 추가 확정한다.
- **질문 생성/출력 중 응답 유실 방지.** UC-02(음성 통화 진행) 중 다음 두 케이스를 구분해서 처리한다: (1) 질문을 생성하는 중에 시니어 음성이 수집되면, 진행 중인 질문 생성을 멈추고 그 응답을 포함해 AI 서버에 재요청한다. (2) 질문을 출력(TTS 재생)하는 중에 음성이 수집되면, 출력은 그대로 유지하고 수집된 응답은 다음 질문 생성 요청에 포함한다. 이전 결과가 뒤늦게 출력되지 않도록 요청마다 `generationId`를 새로 발급하고(`packages/shared-types`의 WS 이벤트 계약, `features/record-voice-answer`의 상태 전이 함수에 반영), 수집된 응답은 `captureId`로 재전송 중복을 방지하며 버퍼링한다(`pendingAnswers`). **서버는 클라이언트가 보낸 phase/generationId를 그대로 신뢰하지 않고, 자신이 들고 있는 generationId 상태로 최종 판단해야 한다** — 클라이언트 상태가 지연·유실됐을 수 있기 때문이다. 이 서버 측 판단 로직 자체는 backend 구현 시 별도 feature 브랜치에서 확정한다.
- **신규 화면 3개, 아직 디자인 없음.** 화면설계서에 화면ID/UC가 배정되어 있지 않다 — 구현 전 화면 설계와 UC/FR 신설이 먼저 필요하다.
