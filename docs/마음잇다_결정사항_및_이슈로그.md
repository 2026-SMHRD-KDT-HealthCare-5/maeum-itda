> 기획서 / 요구사항정의서 / 화면설계서와 함께 참고할 것. **2026-08-08부로 화면별 상세 목업이었던 `docs/page-pdf/`·`docs/page-html/`는 폐기했다** — 팀이 Figma에 화면별 최종 디자인을 반영했기 때문이며, 이제 화면별 최신 디자인의 기준은 Figma다. 아래 표와 §3에 남아있는 `docs/page-pdf/...`·`docs/page-html/...` 인용은 그 결정이 내려질 당시 근거였던 (지금은 삭제된) 파일에 대한 역사적 기록이니 실제 경로가 존재한다고 가정하지 말 것 — 그 화면들의 지금 디자인은 Figma에서 확인해야 한다. Figma 내보내기 파일은 `docs/screens/<화면이름>/`에 저장되어 있다(2026-08-08 기준 11개 화면 폴더 전체에 PNG 반영 완료, `states/` 서브폴더는 참고용 컴포넌트 상태 세트). `docs/데이터베이스요구사항분석서_마음잇다.pdf`·`docs/테이블명세서_마음잇다.pdf`는 새로 추가된 DB 설계 문서로, 아직 이 로그에서 전수 대조되지 않았다 — DB 관련 작업 전에 별도로 검토할 것.
> 아래 내용은 문서 검토 과정에서 별도로 논의·확정된 사항이다. 2026-08-28자로 원본 문서(및 page-html/page-pdf 목업)가 갱신되면서 이 로그의 결정사항 중 일부는 이미 문서에 반영되었고, 일부는 오히려 **번복**되었다 — 아래 표의 "최종 문서 반영 상태" 열을 항상 확인할 것. 이 열이 "미반영"인 항목만 여전히 문서보다 이 로그를 우선한다.

## 0. 최신 프로젝트 구현 방향

2026-08-06에 교체된 기획서와 요구사항정의서를 다시 검토한 결과다. 같은 시점에 두 갈래로 나뉘어 각각 진행된 검토(백엔드 Entity 구현 쪽의 DB·요구사항 대조, 문서 3종 전수 대조)를 하나로 합쳤다.

- 대화 시작 시 WSS 연결을 수립하고, 연결 중 문맥은 별도 세션 테이블이 아닌 백엔드 메모리에서 관리한다.
- 발화 종료 후 완성된 음성은 텍스트 이벤트와 동일한 WebSocket 연결로 멀티플렉싱해 NestJS에 전달한다.
- NestJS는 FastAPI에 분석을 요청하고, FastAPI는 STT·척도 채점·실시간 감성분석·다음 질문 생성·TTS 처리를 담당한다. LLM은 OpenAI API, TTS는 Typecast(Typecast Streaming API)로 벤더가 확정되어 있다.
- STT 결과는 즉시 화면에 노출하지 않고 다음 질문 생성 시점에 직전 응답과 함께 전달한다.
- TTS는 청크 단위로 생성해 동일한 WebSocket 연결로 순차 전송한다.
- 정서지수는 날짜별(00:00~24:00) SGDS-K·GAD-7·LSNS-6 위험 응답 비율만으로 계산한다(TextScore 단일값). acoustic 특징과 실시간 감성분석 결과는 포함하지 않는다.
- 3개 척도 합산 응답이 5문항 미만이면 정서지수 산출을 보류하고 `데이터 부족`으로 처리한다.
- 같은 날 다시 대화하면 해당 날짜 전체 응답으로 정서지수를 재계산하고 기존 일간 리포트를 갱신한다.
- 음성에서 톤·피치·발화 속도를 추출하지만 별도 수치형 음성 점수는 만들지 않는다. 원본 음성은 분석 직후 폐기한다.
- 마지막 발화 후 10분 동안 재연결되지 않으면 메모리 상태를 종료하고 해당 날짜 정서지수 재계산을 실행한다.
- MVP는 연결 상태를 메모리에서 관리하는 단일 백엔드 인스턴스를 전제로 한다.
- 펭귄 마스코트는 앞으로 사용하지 않는다. 시니어 화면은 '다솔'(손녀 페르소나)로 이미 정리되어 있다 — §1 "마스코트 캐릭터 정책" 참고.

### 문서 간 충돌 시 기준

## 2. 아직 안 끝난 것 - 다음 논의에서 이어가야 할 이슈

1. **일간 vs 주간 알림 트리거 통합 여부** — **해결됨.** 요구사항정의서 재수정판 UC-10 선행조건에 "본 알림은 일간 정서지수 산출 시점에만 트리거되며, 주간 리포트(UC-08)는 별도 알림 없이 조회 전용으로 제공된다"로 명시됨. 즉 "일간/주간 두 알림 타입으로 분리"가 아니라 **알림 자체가 일간 트리거 하나뿐이고 주간은 알림 없이 조회만 제공**하는 것으로 정리됨.

2. **알림 `target` 스키마 확장**
   **부분 해결.** 최종 요구사항정의서 UC-11 기본흐름③에 알림 목록 반환 필드가 "유형, 제목, 내용, 대상(리포트 등)" 4-튜플로 구체화되었고, FR-03-04에 알림 유형 3종(연결 요청 / 정서지수 하락 / 리포트 도착)이 명시됨. 다만 유형별 `target` 필드의 실제 타입 정의(예: `{type:'dailyReport', reportId}` 같은 스키마)는 여전히 없음 — `packages/shared-types` 설계 시 확정 필요.

3. **음성 분석 DB 구조 충돌**
   §1 "`voice_score` 이름 충돌" 행(§2-9)에서 애플리케이션 로직은 TextScore 단일값으로 확정됐지만, DB 쪽은 아직 안 따라왔다. 요구사항정의서 FR-02-03·FR-02-04는 acoustic 특징을 정서지수에 포함하지 않고 수치형 음성 점수를 만들지 않는다고 명시하는 반면, 테이블명세서에는 `VOICE_EMOTION_SCORE` 컬럼이 남아 있고 현재 `apps/backend`의 Entity(`voice-emotion-analysis.entity.ts`)도 이를 그대로 따르고 있다. 컬럼을 삭제할지 보조 분석값(정서지수 연산에는 미포함, 참고용 통계로만 저장)으로 유지할지를 팀이 확정한 뒤 DB 명세와 Entity를 함께 수정해야 한다.

4. **근거 문장(evidenceSentences) 소스 범위** — **해결됨.** 요구사항정의서 재수정판에서 UC-09/FR-03-02가 범위를 명시적으로 넓힘: "척도(SGDS-K/GAD-7/LSNS-6) 태그가 부여된 발화는 반드시 포함하며, 척도 태그가 없더라도 실시간 감성분석 결과(`sentiment_label`)가 있는 발화는 해당 라벨과 함께 ... 노출해야 한다"(FR-03-02). 이제 화면 목업(전체 대화 노출)과 문서 스펙이 일치함. 단 여기 쓰이는 건 `sentiment_label`뿐이고 `sentiment_note`는 근거문장 노출과 무관(UC-06-4 일간 요약 생성에만 쓰임) — 혼동하지 말 것.

5. **무한 스크롤과 페이지네이션 표현 충돌**
   FR-01-09는 "무한 스크롤 방식으로 페이지네이션 없이"라고 표현한다. 무한 스크롤도 서버 쪽에서는 cursor 또는 offset 기반의 분할 조회가 필요하므로, 이 표현은 "페이지 번호를 화면에 노출하지 않는다"는 뜻으로 해석한다. 구현 기준은 cursor 기반 무한 스크롤(§5의 `createdAt`+`id` cursor pagination 계약)로 하되, API 계약을 완전히 확정하기 전에 팀 확인이 필요하다.

6. **관리자 역할 범위 충돌**
   로그인 흐름(UC-00)에는 관리자 역할이 포함되지만, 회원가입은 시니어·보호자만 대상으로 하고(FR-00-02), DB `USERS.ROLE`과 현재 `UserRole` 타입도 `SENIOR | GUARDIAN`만 허용한다. 관리자 화면 자체가 MVP 제외 결정(§1)이므로, MVP의 JWT 역할(claim)에 관리자를 추가하는 것도 보류한다 — 관리자 계정 발급/인증 방식이 정해지기 전까지는 손대지 말 것.

7. **문서 내 오탈자** — **해결됨.** DB는 MySQL로 통일(위 표 참고). 3개 원본 문서 표지 날짜도 모두 2026.08.28로 통일되어 역전 문제 해소. (참고: 화면설계서 내부 변경이력 표의 최신 리비전이 이제 v0.4/2026.08.06("시니어 화면 설계 수정")으로, 여전히 표지 날짜보다 앞서 있는 사소한 불일치가 남아있으나 별도 조치 불필요한 수준)

8. **실제 푸시 발송 범위 충돌**
   요구사항정의서 FR-03-03/UC-10은 MVP에서 보호자 스마트폰으로 실제 푸시 알림을 발송한다고 서술하지만, 팀 결정(§1 "웹 푸시 알림" 행)은 PWA 적용 전까지 실제 웹 푸시를 제외하고 알림함(REST 조회)만 구현하는 것이다. 지금은 팀 결정을 우선하되, 발표 자료·요구사항 문서의 문구를 실제 구현 범위와 다시 맞추는 정리 작업이 남아있다.

9. **`voice_score` 이름 충돌** — **해결됨, 그리고 이제 요구사항정의서 본문에도 반영됨.** 팀 결정: turn 단위 `voice_score`/일간 집계 `VoiceScore` 개념 자체를 없앤다. 음성 acoustic feature(톤·피치)는 별도로 수치화하지 않고, UC-04의 실시간 감성분석(`sentiment_label`/`sentiment_note` 생성) 입력 재료로만 사용한다. 정서지수(UC-06-2)는 **TextScore 단일값**으로 산출한다. 최신 요구사항정의서 FR-02-03이 이제 명시적으로 "SGDS-K/GAD-7/LSNS-6 척도별 위험 응답 비율 기반 텍스트 점수를 산출하여 이를 최종 정서지수로 사용해야 한다. 음성 acoustic 특징 및 LLM 기반 감성분석 결과는 본 연산에 포함하지 않는다"고 못박아 팀 결정과 문서가 일치하게 됐다. **다만 프로젝트 기획서(2쪽, 8쪽)는 여전히 "TextScore 70% : VoiceScore 30% 가중 결합"이라는 낡은 공식을 그대로 싣고 있어 두 원본 문서가 서로 상충한다** — 요구사항정의서가 최신 확정 사항이므로(§0 참고) FR-02-03(TextScore 단일값)을 따르고 기획서의 가중 결합 문구는 무시할 것. DB 스키마가 아직 이 결정을 따라오지 못한 부분은 §2-3 참고.

## 4. 향후 확장 대비 아키텍처 원칙

> 팀 전체가 공식적으로 확정한 요구사항은 아니고, 외부 조언을 받아 개발 방향에 반영하기로 한 엔지니어링 원칙. MVP는 웹으로만 구현하되, 나중에 Flutter 앱을 추가할 때 백엔드/AI서버를 다시 짜지 않아도 되도록 아래를 지킨다.

- 백엔드(NestJS) REST API는 OpenAPI(Swagger) 스펙으로 관리 — 추후 Flutter(Dart)용 클라이언트를 스펙 기반으로 생성 가능하게 함
- 실시간 안부 대화 WebSocket 이벤트명·payload 구조는 `packages/shared-types`에 타입으로 고정 — 프론트엔드 코드 안에만 암묵적으로 존재하지 않도록 함
- 인증은 브라우저 쿠키/세션이 아닌 JWT 등 토큰 기반으로 구현 — 모바일 클라이언트도 동일한 인증 흐름 재사용 가능하게 함
- 정서지수 계산, 임계치 판단, 권한 체크 등 비즈니스 로직은 프론트엔드(React)가 아닌 백엔드/AI서버에 위치 — 새 클라이언트가 로직을 재구현할 필요 없게 함

## 5. 2026-08-05 추가 결정사항

- **일간 리포트 집계 단위: turn 단위로 변경(§3의 conversation_id 통합 귀속 규칙 폐기).** 하루의 경계는 서비스 기준 시간대(Asia/Seoul)의 `[당일 00:00, 익일 00:00)` 반개구간이며, DB 저장은 UTC ISO 8601, 일간 조회 요청은 `YYYY-MM-DD`(서비스 기준 시간대)로 받아 백엔드가 UTC 범위로 변환한다. 자정을 넘겨 진행된 통화는 더 이상 시작 시각 기준으로 전체가 한쪽 날짜에 묶이지 않고, turn별로 각자의 귀속 시각이 속한 날짜에 개별 귀속된다 — 하나의 통화가 두 날짜의 리포트에 걸쳐 분리 집계될 수 있다. **귀속 기준 시각은 `createdAt`(질문 생성 시각)이 아니라 `answeredAt`(시니어가 실제 답변한 시각)이다** — `createdAt`은 무한 스크롤 정렬/페이지네이션에만 쓴다. 답변 없이 끝난 turn만 `createdAt`으로 대체 귀속한다(예: 23:59에 질문이 생성됐고 00:01에 답했다면, `answeredAt` 기준으로 "다음날" 리포트에 잡혀야 한다 — 실제 감정 신호가 발생한 시점이 그때이기 때문). 리포트 재생성 시 해당 날짜에 귀속된 모든 유효 turn을 다시 모아 재집계한다.
- **"대화 세션" 컨테이너 개념 삭제.** 여러 turn을 하나의 통화 단위(`Conversation`: `startedAt`/`endedAt`)로 묶는 개념 자체를 없앤다. turn이 독립적인 이력 레코드가 되며, 이 결정에 따라 `packages/shared-types`에 `ConversationTurn` 타입(자체 `createdAt` 포함)을 최초로 고정했고 `apps/frontend`의 `entities/conversation`도 이를 재노출하도록 맞췄다. 단 `entities/user`의 `SessionProvider`/`useSession`은 로그인 인증 세션이라 이번 삭제와 무관 — 계속 유지한다.
- **이전 대화 이력 무한 스크롤.** 시니어 안부 대화 화면(`SENIOR_CONVERSATION_01`)에서 과거 turn 이력을 무한 스크롤로 조회 가능해야 한다. cursor pagination 계약(`createdAt`+`id` 기반), 실시간 WebSocket으로 들어오는 turn과 REST로 가져온 과거 이력의 병합·중복 제거 규칙은 별도 feature 브랜치에서 `packages/shared-types`에 추가 확정한다.
- **질문 생성/출력 중 응답 유실 방지.** UC-02(음성 통화 진행) 중 다음 두 케이스를 구분해서 처리한다: (1) 질문을 생성하는 중에 시니어 음성이 수집되면, 진행 중인 질문 생성을 멈추고 그 응답을 포함해 AI 서버에 재요청한다. (2) 질문을 출력(TTS 재생)하는 중에 음성이 수집되면, 출력은 그대로 유지하고 수집된 응답은 다음 질문 생성 요청에 포함한다. 이전 결과가 뒤늦게 출력되지 않도록 요청마다 `generationId`를 새로 발급하고(`packages/shared-types`의 WS 이벤트 계약, `features/record-voice-answer`의 상태 전이 함수에 반영), 수집된 응답은 `captureId`로 재전송 중복을 방지하며 버퍼링한다(`pendingAnswers`). **서버는 클라이언트가 보낸 phase/generationId를 그대로 신뢰하지 않고, 자신이 들고 있는 generationId 상태로 최종 판단해야 한다** — 클라이언트 상태가 지연·유실됐을 수 있기 때문이다. 이 서버 측 판단 로직 자체는 backend 구현 시 별도 feature 브랜치에서 확정한다.
