# 마음잇다 - 결정사항 및 미결 이슈 로그

> 기획서 / 요구사항정의서 / 화면설계서, 그리고 화면별 상세 목업인 `docs/page-pdf/`(커밋됨)와 함께 참고할 것. `docs/page-html/`도 같은 목업의 인터랙티브 버전이지만 용량 때문에 `.gitignore` 처리되어 있어 로컬에만 있을 수 있음 — 있으면 참고하되 항상 존재한다고 가정하지 말 것.
> 아래 내용은 문서 검토 과정에서 별도로 논의·확정된 사항이다. 2026-08-28자로 3개 원본 문서(및 page-html/page-pdf 목업)가 갱신되면서 이 로그의 결정사항 중 일부는 이미 문서에 반영되었고, 일부는 오히려 **번복**되었다 — 아래 표의 "최종 문서 반영 상태" 열을 항상 확인할 것. 이 열이 "미반영"인 항목만 여전히 문서보다 이 로그를 우선한다.

## 0. 최신 프로젝트 구현 방향

2026-08-06에 교체된 기획서와 요구사항정의서를 다시 검토한 결과다. 기능 동작은 요구사항정의서를 우선하고, DB 구조는 테이블명세서를 따르되 두 문서가 충돌하면 구현 전에 팀 결정을 받아야 한다.

- 대화 시작 시 WSS 연결을 수립하고, 연결 중 문맥은 별도 세션 테이블이 아닌 백엔드 메모리에서 관리한다.
- 발화 종료 후 완성된 음성은 텍스트 이벤트와 동일한 WebSocket 연결로 멀티플렉싱해 NestJS에 전달한다.
- NestJS는 FastAPI에 분석을 요청하고, FastAPI는 STT·척도 채점·실시간 감성분석·다음 질문 생성·TTS 처리를 담당한다.
- STT 결과는 즉시 화면에 노출하지 않고 다음 질문 생성 시점에 직전 응답과 함께 전달한다.
- TTS는 청크 단위로 생성해 동일한 WebSocket 연결로 순차 전송한다.
- 정서지수는 날짜별(00:00~24:00) SGDS-K·GAD-7·LSNS-6 위험 응답 비율만으로 계산한다. acoustic 특징과 실시간 감성분석 결과는 포함하지 않는다.
- 3개 척도 합산 응답이 5문항 미만이면 정서지수 산출을 보류하고 `데이터 부족`으로 처리한다.
- 같은 날 다시 대화하면 해당 날짜 전체 응답으로 정서지수를 재계산하고 기존 일간 리포트를 갱신한다.
- 음성에서 톤·피치·발화 속도를 추출하지만 별도 수치형 음성 점수는 만들지 않는다. 원본 음성은 분석 직후 폐기한다.
- 마지막 발화 후 10분 동안 재연결되지 않으면 메모리 상태를 종료하고 해당 날짜 정서지수 재계산을 실행한다.
- MVP는 연결 상태를 메모리에서 관리하는 단일 백엔드 인스턴스를 전제로 한다.

### 문서 간 충돌 시 기준

1. 이 로그에 기록된 명시적인 팀 확정 결정
2. 기능 동작: 요구사항정의서
3. DB 구조: 테이블명세서
4. 서비스 배경과 장기 방향: 프로젝트 기획서

요구사항정의서와 테이블명세서가 충돌하는 DB 항목은 어느 한쪽을 임의로 적용하지 않고 미결 이슈로 남긴다.

## 2. 아직 안 끝난 것 - 다음 논의에서 이어가야 할 이슈

1. **일간 vs 주간 알림 트리거 통합 여부**
   최종 요구사항정의서에도 여전히 언급 없음. UC-08(일간/주간 리포트 조회)은 조회 전용 UC로만 존재하고, UC-10(정서지수 하락 알림)은 일간 단위 트리거만 서술 — 주간 트리거와의 통합/분리 여부 미결정 그대로.

2. **알림 `target` 스키마 확장**
   **부분 해결.** 최종 요구사항정의서 UC-11 기본흐름③에 알림 목록 반환 필드가 "유형, 제목, 내용, 대상(리포트 등)" 4-튜플로 구체화되었고, FR-03-04에 알림 유형 3종(연결 요청 / 정서지수 하락 / 리포트 도착)이 명시됨. 다만 유형별 `target` 필드의 실제 타입 정의(예: `{type:'dailyReport', reportId}` 같은 스키마)는 여전히 없음 — `packages/shared-types` 설계 시 확정 필요.

3. **음성 분석 DB 구조 충돌**
   요구사항정의서 FR-02-03·FR-02-04는 acoustic 특징을 정서지수에 포함하지 않고 수치형 음성 점수를 만들지 않는다고 명시한다. 그러나 기획서는 TextScore 70% + VoiceScore 30%를 설명하고, 테이블명세서에는 `VOICE_EMOTION_SCORE`가 남아 있다. 현재 Entity는 테이블명세서를 따르므로 컬럼 삭제 또는 보조 분석값 유지 여부를 팀에서 확정한 뒤 DB 명세와 Entity를 함께 수정해야 한다.

4. **무한 스크롤과 페이지네이션 표현 충돌**
   FR-01-09는 “무한 스크롤 방식으로 페이지네이션 없이”라고 표현한다. 무한 스크롤도 서버에서는 cursor 또는 offset 기반 분할 조회가 필요하다. 구현 기준은 페이지 번호를 노출하지 않는 cursor 기반 무한 스크롤로 해석하되 API 계약 확정 전에 팀 확인이 필요하다.

5. **관리자 역할 범위 충돌**
   로그인 흐름에는 관리자 역할이 포함되지만 회원가입은 시니어·보호자만 대상으로 하고, DB `USERS.ROLE`과 현재 `UserRole`도 `SENIOR | GUARDIAN`만 허용한다. 관리자 화면은 MVP 제외 결정이므로 MVP JWT 역할에는 관리자 추가를 보류한다.

6. **실제 푸시 발송 범위 충돌**
   FR-03-03은 MVP에서 보호자 스마트폰 푸시 알림 발송을 요구하지만 팀 결정은 PWA 적용 전까지 실제 웹 푸시를 제외하고 알림함 REST 조회만 구현하는 것이다. 현재는 팀 결정 로그를 우선하되 발표 범위와 요구사항 문구를 다시 맞춰야 한다.

7. **문서 내 오탈자** — **해결됨.** DB는 MySQL로 통일(위 표 참고). 3개 원본 문서 표지 날짜도 모두 2026.08.28로 통일되어 역전 문제 해소. (참고: 화면설계서 내부 변경이력 표의 최신 리비전(v0.3)이 2026.08.03으로 표지 날짜보다 앞서 있는 사소한 불일치가 남아있으나, 별도 조치 불필요한 수준)

## 4. 향후 확장 대비 아키텍처 원칙

> 팀 전체가 공식적으로 확정한 요구사항은 아니고, 외부 조언을 받아 개발 방향에 반영하기로 한 엔지니어링 원칙. MVP는 웹으로만 구현하되, 나중에 Flutter 앱을 추가할 때 백엔드/AI서버를 다시 짜지 않아도 되도록 아래를 지킨다.

- 백엔드(NestJS) REST API는 OpenAPI(Swagger) 스펙으로 관리 — 추후 Flutter(Dart)용 클라이언트를 스펙 기반으로 생성 가능하게 함
- 실시간 안부 대화 WebSocket 이벤트명·payload 구조는 `packages/shared-types`에 타입으로 고정 — 프론트엔드 코드 안에만 암묵적으로 존재하지 않도록 함
- 인증은 브라우저 쿠키/세션이 아닌 JWT 등 토큰 기반으로 구현 — 모바일 클라이언트도 동일한 인증 흐름 재사용 가능하게 함
- 정서지수 계산, 임계치 판단, 권한 체크 등 비즈니스 로직은 프론트엔드(React)가 아닌 백엔드/AI서버에 위치 — 새 클라이언트가 로직을 재구현할 필요 없게 함
