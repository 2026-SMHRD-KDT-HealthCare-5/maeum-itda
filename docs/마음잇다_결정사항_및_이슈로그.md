## 1. 확정된 MVP 결정사항

| 항목 | 확정 내용 |
|---|---|
| 보호자-시니어 연결 기능 | **MVP 제외**. 연결 코드 생성/인증 절차는 고도화 단계에서 추가. MVP에서는 계정(역할 포함)을 DB에 직접 등록하는 방식과 동일하게, 매핑도 관리자가 직접 설정하는 것으로 가정 |
| 정서 상태 라벨 | **좋음 / 보통 / 나쁨** 3단계로 통일 (기존 API 명세의 '높음/낮음' 2단계는 폐기). 점수 구간별 기준값은 추후 확정 필요 |
| 고위험 알림 트리거 시점 | **MVP**: 일간 리포트 생성 완료 시점에 해당 일자 정서지수/발화 내용 기준으로 판단 후 발송. **고도화**: 발화 중 실시간 위험 감지로 전환 |
| SGDS-K 데이터 부족 시 처리 | **고도화 단계에서 결정**. MVP에서는 UC-06-2 대안흐름(문항 3개 미만 시 산출 보류) 그대로 두되, API 응답 스키마(`emotionScore` null 처리 등)는 미정 상태로 둠 |
| 백엔드 기술스택 | **TypeScript, Node.js, Nest.js**로 확정 (기획서 Section 4의 "JavaScript, Express" 표기는 오기이며 무시할 것) |
| 관리자 화면(데이터 품질 검토) | **기획만 하고 MVP 구현 범위에서 제외**. 화면설계서 메뉴구성 트리에는 남아있으나 실제 개발 대상 아님 |

## 2. 아직 안 끝난 것 - 다음 논의에서 이어가야 할 이슈

1. **일간 vs 주간 알림 트리거 통합 여부**
   요구사항정의서(UC-10, 세션·일간 단위 트리거)와 API 명세("AI 서버 기능3", 주간 추이 기반 트리거) 표현이 다름. 하나로 합칠지, 알림 타입 2종(일간/주간)으로 나눌지 미결정.

2. **알림 `target` 스키마 확장**
   화면설계서 알림함 목업에는 알림 유형이 최소 3종 이상(정서지수 하락 / 안부 대화 미완료 / 일간 리포트 도착) 노출되는데, API 명세의 `target` 구조는 `{type:'dailyReport', reportId}` 하나만 정의됨. 유형별 target 스키마 보강 필요.

3. **근거 문장(evidenceSentences) 소스 범위**
   API 주석상 `SGDS_K_RESULT` 테이블 한정이라고 되어 있으나, 화면설계서 리포트 목업은 일반 대화 내용까지 근거 문장으로 노출. SGDS-K 문항 한정인지 전체 대화(Chats) 포함인지 확정 필요.

4. **문서 내 사소한 오탈자 정리 필요**
   - 요구사항정의서 NFR-SE-003: DB가 PostgreSQL로 잘못 표기됨 (MySQL로 통일 필요)
   - 기획서·요구사항정의서 표지 날짜(2026.08.28)가 화면설계서(2026.07.28)보다 늦음 → 문서 작성 순서에 맞게 날짜 재정리 필요

## 4. 향후 확장 대비 아키텍처 원칙

> 팀 전체가 공식적으로 확정한 요구사항은 아니고, 외부 조언을 받아 개발 방향에 반영하기로 한 엔지니어링 원칙. MVP는 웹으로만 구현하되, 나중에 Flutter 앱을 추가할 때 백엔드/AI서버를 다시 짜지 않아도 되도록 아래를 지킨다.

- 백엔드(NestJS) REST API는 OpenAPI(Swagger) 스펙으로 관리 — 추후 Flutter(Dart)용 클라이언트를 스펙 기반으로 생성 가능하게 함
- 실시간 안부 대화 WebSocket 이벤트명·payload 구조는 `packages/shared-types`에 타입으로 고정 — 프론트엔드 코드 안에만 암묵적으로 존재하지 않도록 함
- 인증은 브라우저 쿠키/세션이 아닌 JWT 등 토큰 기반으로 구현 — 모바일 클라이언트도 동일한 인증 흐름 재사용 가능하게 함
- 정서지수 계산, 임계치 판단, 권한 체크 등 비즈니스 로직은 프론트엔드(React)가 아닌 백엔드/AI서버에 위치 — 새 클라이언트가 로직을 재구현할 필요 없게 함
